# Кеширование

## Анализ системы

В системе наблюдаются проблемы со скоростью работы веб-приложения MES, что влияет на качество работа Операторов с заказами. Ранее были предприняты попытки решения данной проблемы - реализация фильтра по статусам и пагинация, но данное решение не помогло.

## Мотивация

Операторам важно видеть самые новые заказы, потому что от этого зависит их вознаграждение, — кто взял заказ, тот и получит оплату. Кэширование списка заказов, возвращаемых сервисов MES API позволит решить проблему долгой загрузки дашборда операторов.

## Предлагаемое решение

Внедрение **серверного** кеширования позволит сохранить целостность данных отображаемых операторам и позволит инвалидировать кэш при создании новых заказов и при изменении статуса заказа. Реализовать данную валидацию позволит паттерн кэширования **Cache-Aside**.

### Сравнение паттернов

**Cache-Aside:**

- Прост в реализации;
- Устойчив к сбоям, что важно для работы операторов;
- Оптимизирует чтение, основное узкое место приложения MES;
- Операция записи выполняется в базу данных, что позволит видеть актуальные данные сразу всем компонентам системы.

**Write-Through**:

- Кеш является вспомогательным сервисом БД, лучше чтобы его реализовывали разработчики БД;
- Модель данных в кеше должна быть идентична модели базы данных, это затруднит обогащение данны.

**Refresh-Ahead**:

- Обновление данных происходит асинхронно, что может привести к неконсистентности данных.

### Стратегия инвалидации кеша


| По ключу | Программная | На основе изменений |
| -------- | ----------- | ------------------- |
| Позволяет точно определять данные, которые нуждаются в обновлении | Позволяет гибко управлять инвалидацией кэша | Для обновления данных в реальном времени |
| При создании заказа или изменении статуса очищается кеш только для изменённого заказа по его уникальному идентификатору | При каждом запросе взятие в работу заказа оператором, система программно инвалидирует кеш, если количество доступных заказов изменилось | При добавлении нового заказа система инвалидирует кеш дашборда, чтобы отобразить новый заказ |
| Помогает минимизировать объём инвалидации и обновлять только необходимые данные, улучшая производительность и уменьшая нагрузку на систему | Гарантирует, что операторам будет показана актуальная информация о доступности заказов и они не будут пытаться взять в работу занятый заказ | Операторы смогут видеть актуальные данные, даже если другие операторы берут заказы |
| Помогает обновлять данные заказа, но так как он не меняется, а важна только актуальность статуса, данный метод не подходит | Сложнее в реализации, но обеспечит гибкость и контроль над инвалидацией кеша в соответствии с логикой и потребностями приложения | Проста в реализации, но каждый раз после инвалидации будет выполняться тяжелый запрос на заполнение кэша |

С учетом приведенного сравнение, лучше использовать **программную** инвалидацию. Хоть она и не проста в реализации, но позволит операторам видеть актуальные данные и интегрироваться с существующей пагинацией и фильтрацией.
